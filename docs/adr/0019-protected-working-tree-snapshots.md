# ADR 0019：受保护的未提交工作区快照

## 状态

已采纳，适用于 `v0.19.0`。

## 背景

此前真实任务必须从干净的 Git `HEAD` 开始。这给隔离 worktree、Diff 和验收契约提供了稳定基准，但也迫使用户在试用前提交或 stash 尚未完成的工作。临时 Commit 会污染历史，stash 则改变工作区状态并存在恢复冲突风险。

系统不能直接在脏工作区运行 Agent：用户原有修改和 Agent 修改将难以区分，失败回滚可能覆盖文件，规划与执行之间的内容漂移也会使验收契约失效。

## 决策

- 项目仍必须是至少包含一个 Commit 的 Git 仓库；空仓库不支持快照。
- 创建任务前通过本地 API 检查仓库，页面只展示 HEAD、语言和变化文件名，不返回文件内容。
- 发现已跟踪修改、删除或未跟踪文件时，必须由用户显式确认纳入快照。
- 快照使用独立临时 Git index 对当前工作树执行 `read-tree`、`add --all` 和 `write-tree`，不改动原 index、当前分支或工作区文件。
- 系统通过 `commit-tree` 创建快照基线，并保存在 `refs/amor/snapshots/<commit>`，以防任务等待期间被 Git 垃圾回收。该 ref 不是本地分支，不会被普通 push 自动发布。
- 规划、Agent 执行和补丁交付都从同一个快照 Commit 创建独立 worktree。契约中的 `baseline_commit` 因而覆盖用户确认时看到的完整文件状态。
- Job Artifact 保存源 HEAD、tree hash、基线 Commit、内部 ref 和变化文件名，不保存额外文件副本。
- 在回答规划问题、批准执行和交付补丁前，重新计算源工作区的 HEAD 与 tree hash；任一变化都会拒绝继续，要求创建新任务。
- 交付到新本地分支时保留快照 Commit，因此分支同时包含用户原有未提交内容和 Agent 已验收修改。页面明确提示这一事实。
- 基于工作区快照的交付不能使用自动 GitHub Draft PR 发布，避免把原本未提交的私有修改意外推送；用户必须先人工审阅和整理 Commit。
- 仅有脏 submodule 状态而无法形成不同 tree 的仓库拒绝快照，不宣称捕获 submodule 内未提交文件。

## 结果

用户可以在不改变当前文件、分支和暂存区的情况下让 AMOR 理解并修改正在进行的项目。任务仍拥有稳定、可复验的 Git 基线，并能检测规划后的漂移。

代价是仓库对象库中会保留小型快照 Commit 和 `refs/amor/snapshots/` 引用；这是保证任务可在服务重启后继续的有意选择。后续版本可以在提供可审计的任务删除和保留策略后增加显式清理功能。
