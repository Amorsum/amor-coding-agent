# ADR 0008：真实项目采用验证驱动的有限修复闭环

## 状态

已接受，随 `v0.8.0` 实施。

## 背景

此前模型在通过可见测试并检查 Diff 后请求最终验收，独立 Verifier 一旦拒绝，真实项目运行会直接结束。固定 Token 上限也在模型已经返回 `submit_for_verification` 时先于工具处理生效：调用费用已经产生，本地 Verifier 却不再执行。这既没有节省已发生的成本，也会把已经完成修改和测试的任务标记为 Agent Loop 失败。

真实项目与 Benchmark 的目标不同。真实项目优先完成用户任务，适合利用验收反馈继续修复；Benchmark 必须保持隐藏测试的一次性，不能把隐藏反馈交给模型后重试。

## 决策

- `amor run` 在启动模型前写入 `verification-contract.json`，固化任务、验收条件、允许写入范围、用户批准的验证命令和基准提交，并对规范化内容计算 SHA-256。
- 真实项目的独立 Verifier 失败后，把失败检查的摘要作为原 `submit_for_verification` 调用结果返回同一 Provider 会话，在同一隔离 worktree 中继续修复。
- 默认最多追加两次验证驱动修复，可用 `--max-verification-retries` 设置为 0 至 10。
- 每次重试都必须重新运行用户批准的验证命令、重新检查 Diff，并再次主动请求最终验收。
- 最终报告保留 `verification_history` 和总验证次数，不用最后一次结果覆盖此前证据。
- Benchmark 不根据隐藏测试反馈重试，避免污染可复现实验。
- 累计模型 Token 达到 80% 时向 Agent 注入收尾提示。超过硬上限时不执行普通工具调用；如果该轮只有 `submit_for_verification`，且之前已经通过可见验证并检查非空 Diff，则允许执行本地 Verifier，并记录超额数量。

## 后果

- Verifier 从一次性终点变成真实任务的受控反馈来源，满足原项目方案中“验证失败后至少完成一次有效修复”的要求。
- Agent 不能改变验收契约或批准新的命令；反馈循环继续受到总轮次、时间、Token、路径策略和无进展检测约束。
- Token 上限允许最后一个模型轮次产生可观测超额，但不会在超额后发起新的模型请求。
- 当前验收契约仍由用户 CLI 参数构成；本迭代不引入独立测试设计 Agent，也不把自然语言验收条件自动转换为可信测试。
- 当前进程退出后不能恢复未完成的模型会话，验证驱动修复仅发生在同一次运行内。
