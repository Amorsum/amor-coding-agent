# ADR 0011：验收契约采用不可变修订链

## 状态

已接受，随 `v0.11.0` 实施。

## 背景

`v0.10.0` 已允许用户在网页中创建任务和审批契约，但规划状态为 `NEEDS_INPUT` 时只能重新创建任务；已经生成的契约也不能修改。这会丢失问题、回答与先前规划证据之间的关系，并让用户为了修正一句验收条件而重复消耗完整规划成本。

## 决策

1. Job 保存按序号排列的不可变契约修订。每个修订记录来源、说明、时间、Artifact 路径和 SHA-256，当前契约始终指向最新修订。
2. `NEEDS_INPUT` 任务接受对当前问题的完整回答。请求必须携带当前契约哈希，问题集合必须与当前契约完全一致，避免回答过期或被替换的问题。
3. 回答不会交给执行 Agent。独立只读规划器获得上一版契约和回答历史，只修改受回答影响的部分；如仍有实质歧义，可以产生下一轮问题。
4. 用户可以在 `NEEDS_INPUT` 或 `AWAITING_APPROVAL` 阶段直接修改契约文本、允许路径和验证命令。人工保存会清空规划问题并形成 `READY` 修订；模型生成的结构化外部用例在网页中保持只读。
5. 修订前再次验证原仓库工作区干净且 HEAD 等于契约基准提交。仓库发生变化时拒绝修订，要求创建新任务。
6. 每次修订重新计算规范 JSON 的 SHA-256，并清除已有执行设置。批准接口只接受最新哈希，因此旧页面、旧审批和并发修改都不能启动 Agent。
7. v0.10 的持久任务在加载时补记为第一版契约，不改写原契约内容。服务重启后继续保留回答与修订历史。

## 理由

不可变修订比原地覆盖更容易审计，也能明确区分模型规划、用户回答和人工修改。乐观并发哈希把“我审批的是哪一版契约”变成后端可验证的事实，而不是前端约定。完整问题匹配和基准提交检查则防止回答或测试标准绑定到已经变化的上下文。

## 限制与后续

- 重规划仍是一次新的模型会话，会产生额外 Token；“局部”表示保留未受影响的契约语义，不代表模型 API 只处理局部文本。
- 人工编辑暂不允许在网页中改写结构化 Python 用例。需要改变这些用例时，应回答规划问题让独立规划器重建，或重新创建任务。
- 当前修订历史展示元数据；契约 JSON 保存在 Job Artifact 中并可通过只读 API 获取，尚未提供两个历史版本的可视化 Diff。
- 任务开始执行后契约永久冻结，不能边执行边修改验收标准。
